### ROS
机器人控制系统，不是传统意义上的操作系统，而是：机器人软件的通信框架 + 工具集 + 软件生态

```text
激光雷达程序
      ↓
SLAM程序
      ↓
路径规划程序
      ↓
MPC控制程序
      ↓
电机驱动程序
```

这些程序可以分别作为 ROS 的 Node（节点）

节点之间通过：

```text
Topic
Service
Action
Parameter
TF
```

等等进行通信

现在学习的一般是 ROS 2

### SLAM
Simultaneous Localization And Mapping：同时定位与建图

机器人进入未知环境中：不知道地图 + 不知道自己在哪里

通过：

```text
LiDAR
Camera
IMU
Wheel Odometry
```

不断估计机器人的 x,y, $\theta$，同时建立 map

### Planning
SLAM 告诉机器人：

> “你在这里，地图长这样。”

Planning 则回答：

> “那我要怎样从 A 走到 B？“”

就是轨迹规划  
经典算法：

```text
Dijkstra
A*
Theta*
Hybrid A*
RRT
RRT*
```

由给出的跟踪轨迹的坐标，计算出所需的控制量，让机器人真正跟踪轨迹

常见的为 PID 控制  
再往后为：

```text
Pure Pursuit
Stanley
LQR
MPC
MPPI
```

### 点云生成

```python
sensor_lidar/src/scan_to_cloud_node.cpp
```

整体的逻辑为：

```text
订阅：

/scan_filtered
       ↓

laser_geometry::LaserProjection
       ↓

PointCloud2
       ↓

发布：

/cloud_filtered
```

就是将之前的二维极坐标转换为直角坐标系坐标：

$$
x=r\cos\theta\quad y=r\sin\theta
$$

代码部分为：

```c++
#include <ros/ros.h>
#include <sensor_msgs/LaserScan.h>
#include <sensor_msgs/PointCloud2.h>
#include <laser_geometry/laser_geometry.h>

#include <string>

class ScanToCloudNode {
public:
    ScanToCloudNode()
        : nh_(), pnh_("~") {
        pnh_.param<std::string>("input_topic", input_topic_, "/scan_filtered");
        pnh_.param<std::string>("output_topic", output_topic_, "/cloud_filtered");

        scan_sub_ = nh_.subscribe(input_topic_, 10, &ScanToCloudNode::scanCallback, this);
        cloud_pub_ = nh_.advertise<sensor_msgs::PointCloud2>(output_topic_, 10);

        ROS_INFO_STREAM("scan_to_cloud_node: " << input_topic_ << " -> " << output_topic_);
    }

private:
    void scanCallback(const sensor_msgs::LaserScan::ConstPtr& scan_msg) {
        if (scan_msg->ranges.empty()) {
            ROS_WARN_THROTTLE(2.0, "scan_to_cloud_node: received an empty LaserScan.");
            return;
        }

        sensor_msgs::PointCloud2 cloud_msg;
        projector_.projectLaser(*scan_msg, cloud_msg);
        cloud_pub_.publish(cloud_msg);
    }

    ros::NodeHandle nh_;
    ros::NodeHandle pnh_;
    ros::Subscriber scan_sub_;
    ros::Publisher cloud_pub_;
    laser_geometry::LaserProjection projector_;
    std::string input_topic_;
    std::string output_topic_;
};

int main(int argc, char** argv) {
    ros::init(argc, argv, "scan_to_cloud_node");
    ScanToCloudNode node;
    ros::spin();
    return 0;
}

```

**问题**：现在几个外参和一个内参还没有确定（用于雷达和相机之间的转换）

K,R（雷达和相机之间的真实旋转外参根本还没有填进去。）,T 都是占位符

```text
雷达点 P_lidar = [x, y, z]ᵀ   (雷达坐标系)

      │  R, T (外参: 雷达→相机)
      ▼
P_camera = R · P_lidar + T    (相机坐标系)

      │  K (内参: 相机→像素)
      ▼
[u, v] = K · P_camera / z     (像素坐标系)
```

#### K——相机内参矩阵
相机怎么把 3D 点投影到 2D 图像上：

$$
K=\begin{bmatrix}f_x&0&c_z\\0&f_y&c_y\\0&0&1\end{bmatrix}
$$

标定时就要标定 K（由焦距以及主点决定），还有就是相机的畸变系数  
标定的方法：（棋盘格标定法）

```text
步骤：
1. 打印黑白棋盘格，贴平板上
2. 从不同角度/距离拍 15~30 张图
3. 检测每张图的棋盘角点 (已知真实间距)
4. 求解 K 和畸变系数
```

使用的工具为：

```bash
# ROS 一键标定
rosrun camera_calibration cameracalibrator.py --size 8x6 --square 0.025
```

#### R — 旋转外参 (Rotation Extrinsic)
回答：" 雷达坐标系相对相机坐标系的朝向差多少 "，3×3 旋转矩阵。

$$
R=\begin{bmatrix}r_{11}&r_{12}&r_{13}\\r_{21}&r_{22}&r_{23}\\r_{31}&r_{32}&r_{33}\end{bmatrix}
$$

```text
典型安装（雷达在前，相机在后上方）：
相机坐标系:       雷达坐标系:
   z(前)            z(前)
   ↑                ↑
   |→ y(左)         |→ y(左)
  /                /
 x(下)            x(下)

两者通常只差一个固定角度（安装角），R 就是这个角度
```

#### T — 平移外参 (Translation Extrinsic)
回答：" 雷达相对相机偏移了多远 "，3×1 向量。

$$
T=\begin{bmatrix}t_x\\t_y\\t_z\end{bmatrix}
$$

```text
例：雷达装在相机正下方 0.1m、前方 0.05m
    → T ≈ [0, 0, 0.05] 或 [0, -0.1, 0.05]（取决于轴定义）
```

对上面的三个参数，可以使用联合标定的方法：

```text
原理：
  同一块棋盘格/标定板，同时被雷达和相机"看到"
      ↓
  相机：检测到棋盘角点的像素坐标 (u, v)
  雷达：检测到标定板平面的点云（得到平面方程）
      ↓
  建立 "3D雷达点 ↔ 2D像素点" 的对应关系
      ↓
  PnP 求解 → 得到 R, T
```

### link：
在 ROS 机器人模型里，一个 link 可以理解成：

> 机器人某个刚体部件所绑定的坐标系。

比如 `laser_link` 表示：

> 以激光雷达自身为原点建立的坐标系。

雷达测到一个点：

```text
x = 2 m
y = 0.5 m
```

实际上完整意思是：

> 这个障碍物在 laser_link 坐标系下，位于雷达前方 2 m、左侧 0.5 m。

而不是“整个地图中的位置”。

所以必须通过 TF：

```text
laser_link  
   ↓  
base_link  
   ↓  
odom  
   ↓  
map
```

把它转成其他坐标系下的位置。

### base_link：机器人的主体坐标系
我们小车的代码定义在后轴中心，轮轴高度处

而 `base_footprint`：机器人在地面上的投影中心：就是对 `base_link` 投影到地面平面上，用于 2D 

### odom
里程计坐标系

> 机器人从启动位置开始，靠轮编码器、IMU、视觉或者其他里程计累计计算出来的位置

机器人先向前走再转弯，相对于启动位置：

```text
x ≈ 2.5
y ≈ 0.8
yaw ≈ 45°
```

虽然优点是连续、平滑，但是缺点是长时间会漂

### map
整个实验室的固定世界坐标系（最全局的坐标）  
map 作为一个长期定位的需要

| 坐标系         | 谁产生         | 主要特点     | 作用         |
| ----------- | ----------- | -------- | ---------- |
| `map`       | SLAM / AMCL | 全局准确，可修正 | 地图、全局定位、规划 |
| `odom`      | 编码器/IMU/里程计 | 连续平滑，但会漂 | 短期定位、控制    |
| `base_link` | 机器人本体       | 跟着机器人移动  | 机器人自身坐标    |

### 整体：

```text
                 SLAM
                   │
                   ↓
map ──────→ odom
                   │
               Odometry
                   │
                   ↓
            base_footprint
                   │
                   ↓
              base_link
              /    |    \
             /     |     \
        Camera   IMU    LiDAR
```

### 关系

$$
\begin{equation}
    ^{map}T_{base}={}^{map}T_{odom}\cdot{}^{odom}T_{base}
\end{equation}
$$

> 机器人在 map 中的位置  
>         =  
> map → odom 的校正  
>         ×  
> odom → base_link 的连续里程计位置

> [!important]+ map 理解  
> map 是机器人的“全局位置估计参考系”，而**不是绝对真实位置**。（也就是 map 也是**预测出来的位置，只不过是修正过的**，稍微准确一点的参考）（而 odom 完全是为了控制连续产生的，误差会不断积累，但是又不能直接修改 odom 的值消除，所以需要 map 作为其消除误差后的真实位置预测值）

> [!tip]+ odom 的理解  
> 这个是完全正确的  
> 根据：
>
>> 轮编码器  
>> IMU  
>> 视觉里程计  
>> LiDAR odometry
>
> 不断在 odom 原点上进行积分：

$$
\begin{equation}
    \begin{gathered}x_{k+1}=x_{k}+\Delta x\\y_{k+1}=y_k+\Delta y\\\theta_{k+1}=\theta_k+\Delta\theta\end{gathered}
\end{equation}
$$

因为这样做是连续的，所以控制器要用 odom，而不是由传感器判断位置

但是：

> `map` 和 `odom ` 的原点没有要求必须相同。  
> 两者之间的修正不是修正 odom 坐标系下的机器人位置，而是坐标变换，使得这个位置为两个不同坐标系下的等价位置，从而达到不修改坐标值，但是不会发生偏移的问题（机器人坐标对齐）

#### 总的来说

> odom 坐标系由轮速计、IMU 或其他里程计连续积分得到，具有良好的局部连续性，但会随时间累积漂移。SLAM 或定位算法利用激光雷达、摄像头以及已有地图等环境观测，对机器人全局位姿进行修正，并通过调整 map→odom 变换补偿里程计漂移，而不会直接修改连续的 odom→base_link 变换。

然后：

> 全局规划通常在 map 坐标系下进行，而局部规划与控制通常更依赖连续的 odom/base_link 坐标。通过 TF 链

$$ map\rightarrow odom\rightarrow base\_link $$

可以在全局地图、里程计坐标系以及机器人自身坐标系之间进行位置转换。

最后：

> RViz 中显示的机器人位置同样是定位系统估计得到的 map→base_link 位姿，并非物理世界的绝对真值。若机器人自身定位存在误差，则地图中的目标点转换至机器人坐标系后也会产生相应误差，从而影响局部规划和控制。

> [!tip]+ 一句话：  
> map  
> = 我在整个世界中“估计”在哪里  
> odom  
> = 根据自身运动推算“我从启动以来走到了哪里“”  
> base_link  
> = 以我自己为原点，东西现在在我的前后左右哪里

```text
map → odom
```

> 就是：**全局定位系统对局部里程计累计误差的修正。**

### 建图和定位的关系

| 阶段      | 地图    | LiDAR | Odom | IMU    | 输出                  |
| ------- | ----- | ----- | ---- | ------ | ------------------- |
| SLAM 建图 | 一开始没有 | ✅核心   | 推荐   | 可选     | `/map` + `map→odom` |
| AMCL 定位  | 已有地图  | ✅核心   | ✅核心  | 通常不直接用 | `map→odom`          |

> LiDAR/Camera 负责“看环境，纠正我在哪里”；Odom/IMU 负责“根据自身运动预测我到了哪里”。

## 雷达里程计
- 初始操作：`source devel/setup.bash`
- `scan_matcher.cpp`：实现的是点 - 线 ICP（Point-to-Line Iterative Closest Point）。被 CMake 编译成静态库 `lidar_scan_matcher`：
- `lidar_odometry_node.cpp `：节点：

```text
/scan 回调
  ↓
1) preprocessScan: LaserScan → 二维点云
   - 距离过滤 (0.15 ~ 8.0 m)
   - 孤立点过滤 (与左右邻点距离 > 0.25 m 视为噪声)
   - 步长抽样 (point_stride=2)
   - 把点从 laser 坐标系 变换到 base_footprint
  ↓
2) publishDebugCloud: 发布预处理后的点云到 /lidar_odometry/preprocessed_cloud（RViz 可视化用）
  ↓
3) processScanMatching:
   - 第一次来：把当前帧存为 reference，发布零位姿 odom
   - 之后：用 ScanMatcher 求 current→reference 的 2D 刚体变换
   - isMatchAccepted 质量门禁 (correspondences / inlier / residual / 跳变 / 速度)
   - 通过：composePoses 累计到 odom_pose_，更新 reference
   - 不通过：丢弃该帧（不污染位姿）
  ↓
4) publishOdometry:
   - 发 /odom_lidar (nav_msgs/Odometry)
   - 发 /lidar_odometry/path (nav_msgs/Path)
   - 发 TF: odom → base_footprint
```

- `lidar_odometry.launch`：启动入口：

```xml
<node pkg="lidar_odometry"
      type="lidar_odometry_node"     ← 编译出来的可执行文件

  <rosparam command="load" file=".../lidar_odometry.yaml" />
  <param name="input_topic" value="$(arg input_topic)" />  ← 默认 /scan，可在 launch 时覆盖
</node>
```

## 数学代码
### ICP
ICP 在最小化一个非线性目标函数

$$
\begin{equation}
    f(T)=\sum_i\rho\left(\mathbf{n}_i\cdot(Rp_i+t-q_i)\right)^2
\end{equation}
$$

> 把 " 当前帧的点 " 通过一个刚体变换 T 投到 " 参考帧 "，让每个点尽可能贴到参考帧里对应的那条直线上。

$$
\begin{equation}
    r_i(T)=\mathbf{n}_i\cdot\begin{pmatrix}R(\theta)p_i+t-q_i\end{pmatrix}
\end{equation}
$$

![](png/Pasted%20image%2020260902151050.png)

最后最小化这个类似距离的目标函数：$\begin{equation}f(T)=\sum_{i\in\mathcal{C}(T)}w_i\cdot r_i(T)^2\end{equation}$

```text
stationary_enter_translation:  0.008 m       ← 运动→静止 阈值
stationary_enter_rotation:     0.006 rad
stationary_confirm_frames:     8             ← 运动→静止 帧数
stationary_exit_translation:   0.015 m       ← 静止→运动 阈值
stationary_exit_rotation:      0.010 rad
motion_confirm_frames:         3             ← 静止→运动 帧数
```

> [!tip]+ 阈值  
> 静释放 = 连续 3 帧 raw pose 偏离 published pose ≥ 0.015 m / 0.010 rad 才解除静止；  
> 动入静 = 连续 8 帧帧间增量 ≤ 0.008 m / 0.006 rad 才进入静止。  
> 非对称设计：退出快（响应真实运动）、进入慢（防误锁）。

先录制五类数据：

1. 增加评测统计：总帧数、各类拒绝次数、ICP 迭代次数、最终步长、RMSE、耗时。(ok)

`rqt_graph` 默认配色（**Nodes/Topics/Service** 视图全开时）：

| 形状 | 颜色 | 含义 |
|------|------|------|
| 圆角矩形 | **蓝色** | **Node**（节点）—— 图里就是 `/lidar_odometry_node` 主体 |
| 圆角矩形 | **红色** | **Service**（服务）—— 下面那个 `/lidar_odometry_node/get...`，大概率是 `get_state` / `get_covariance` 之类的同步服务调用 |
| 菱形 | **紫色** | **Topic**（话题）—— `/odom`、`/lidarentry`、`/preprocessedcloud`、`/path` |
| 实线/虚线 | 灰色 | **连接关系**：节点 ↔ 话题，箭头方向 = 发布方向（publisher → topic → subscriber） |

1. **双斜杠 `//odom`、`//path` **  
   不是路径，是**话题名前缀重复**。通常是：
   - 节点被放到一个以 `/` 结尾的命名空间（`ns:="/"`），或
   - 话题重映射时多塞了个 `/`（比如 `~odom` 被解析成 `/<ns>//odom`）。  
   修法：在 launch 里**统一**用一个 namespace + 相对话题名（`~odom` 而不是 `~ /odom`），或者把重映射写成 `odom:=odom` 而不是 `odam:=/odom`。

2. **蓝色节点向上方一片灰色的 " 蜘蛛网 "**  
   那是 `rqt_graph` 把 `/tf`、`/tf_static`、`/rosout`、`/parameter_events` 这些**几乎所有节点都会连的系统级话题**画出来当作背景噪声。可以在左上角 `Topics` 框里**取消勾选** `Diagnostic`、`TF`、`Parameter` 这几项，画面立刻清爽。

3. **如何判断红色块是不是 service**  
   看它和谁连：
   - 跟 topic 一样从**发布节点指向红色块** + 从**红色块指向订阅节点** = service（请求/响应）
   - 而真正的 topic pub/sub 是**发布节点 → topic → 订阅节点**（中间那个菱形就是 topic）  
   所以图里这种 " 线从蓝节点直接连到红块、不经过菱形 " 的就是 service。

4. **隐藏 service 看纯拓扑**  
   `Hide` 区把 `Services`、`Actions` 勾掉，紫色菱形 + 蓝色节点 = 纯 pub/sub 拓扑，调数据流时更直观。

如果你把 `rqt_graph` 截图贴全（或者直接告诉我 " 启动时输出哪些 topic"），我可以帮你判断 `//odom` 这个双斜杠到底是 launch 里哪个参数搞出来的。

#### 通信原理
ROS 识别主要有四层“标签”

| 层级     | 例子                      | 作用                   |
| ------ | ----------------------- | -------------------- |
| 话题名称   | `/scan`                 | 表示数据频道               |
| 消息类型   | `sensor_msgs/LaserScan` | 规定消息内部结构（数据结构标签）     |
| 字段名称   | `ranges`、`angle_min`    | 表示具体信息               |
| Header | `stamp`、`frame_id`      | 表示采集时间和坐标系（单条信息的元信息） |

```text
/sc_mini节点
  ↓ 发布 /scan
lidar_odometry_node
  ↓ 每收到一帧执行scanCallback
读取：
  header.stamp
  header.frame_id
  angle_min
  angle_increment
  range_min/range_max
  ranges[]
  ↓
过滤Infinity和越界点
  ↓
扫描匹配
  ↓
发布 /odom_lidar 和 /lidar_odometry/path
```

```text
主动（你写的代码）：                        被动（ROS 在背后做的）：
─────────────────                          ─────────────────
1. 写一个函数 scanCallback(LaserScan)      3. 起一个监听线程，
2. 在 main 里告诉 ROS：                       不断问 ROS Master：
   "以后 /scan 来消息                         "有没有新消息？"
    就调这个函数"                                 ↓
       ↓                                    有！
       ↓                                        ↓
   ros::spin();  ← 阻塞在这里                 4. 把你注册的 scanCallback
   （主线程死循环）                             拿出来用消息作为参数调用一次
                                                    ↓
                                            scanCallback 里所有代码执行完
                                                    ↓
                                            5. 返回 spin()，继续等下一帧
```

```text
/sc_mini (发布者)                              lidar_odometry_node (订阅者)
─────────────────                              ──────────────────────
  scanCB 它不知道                                scanCallback 在这里定义
  scanCB 它不关心                                scanCallback 在这里执行
  不知道谁会订阅                                  nh.subscribe(..., scanCallback)
         ↓                                              ↓
  ros::Publisher pub = 
  nh.advertise<...>("/scan");                        ros::spin();
         ↓                                              ↓
  pub.publish(msg);  ← 把消息扔到 ROS 总线上         监听总线，来了就调 scanCallback
         ↓
  它的工作就完了 ✅
```

### 可以作为真值的数据

最实用的是下面这些。

1. 静止真值

初始和结束各 15 秒内：

```text
真实位移 = 0
真实速度 = 0
真实航向变化 = 0
```

可以评价：

- 最大静止漂移
- 最终静止漂移
- 静止门控误释放次数
- 动态障碍物经过时的最大位置跳动

2. 实际纵向距离

以 `base_footprint` 对应的车体基准点为准，在地面标记起点和终点，用卷尺测量：

```text
d_true = 实际纵向距离
e_long = 里程计纵向距离 - d_true
```

不要用车头作为基准，因为车头姿态偏转会影响测量。

3. 横向偏差

在地面拉直线或使用激光水平仪：

```text
e_lateral = 终点相对参考直线的横向距离
```

这可以检查小车实际跑偏和里程计横向估计误差。但要区分：车辆真的跑偏不等于里程计算错。

4. 终点航向角

在车体上选择前后两个固定基准点，测量终点车身方向与起始直线的夹角：

```text
e_yaw = yaw_estimated - yaw_measured
```

基准点间距越长，角度测量越准确。

5. 平均速度参考

```text
平均真实速度 = 实际测量距离 / 实际运动阶段时间
```

阶段时间可由 `/lidar_odometry/test_phase` 中的 `DRIVING` 起止时刻获得。但这只能作为整段平均速度，不能代表瞬时速度。

6. 小场地最推荐的连续真值

在场地上方或侧上方安装固定相机，在车顶贴 AprilTag：

```text
固定相机 + AprilTag
→ 连续测量车辆 x、y、yaw
→ 与 /odom_lidar 对齐
→ 计算整段轨迹误差
```

这比只测终点更全面，而且非常适合你现在的小场地。

不能当作独立真值的包括：

```text
/cmd_vel：只是控制输入
/odom_lidar：是被测结果
原有雷达里程计轨迹：仍然是被测算法输出
```

轮编码器经过标定后可以作为对照参考，但轮滑时也会有误差。第一阶段使用“静止零运动 + 卷尺纵向距离 + 横向直线 + 终点航向”已经足以比较第一轮参数优化。
