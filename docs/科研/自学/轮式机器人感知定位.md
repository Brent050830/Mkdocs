### ROS
机器人控制系统，不是传统意义上的操作系统，而是：机器人软件的通信框架 + 工具集 + 软件生态

```text
激光雷达程序
      ↓
SLAM程序
      ↓
路径规划程序
      ↓
MPC控制程序
      ↓
电机驱动程序
```

这些程序可以分别作为 ROS 的 Node（节点）

节点之间通过：

```text
Topic
Service
Action
Parameter
TF
```

等等进行通信

现在学习的一般是 ROS 2

### SLAM
Simultaneous Localization And Mapping：同时定位与建图

机器人进入未知环境中：不知道地图 + 不知道自己在哪里

通过：

```text
LiDAR
Camera
IMU
Wheel Odometry
```

不断估计机器人的 x,y, $\theta$，同时建立 map

### Planning
SLAM 告诉机器人：

> “你在这里，地图长这样。”

Planning 则回答：

> “那我要怎样从 A 走到 B？“”

就是轨迹规划  
经典算法：

```text
Dijkstra
A*
Theta*
Hybrid A*
RRT
RRT*
```

### control
由给出的跟踪轨迹的坐标，计算出所需的控制量，让机器人真正跟踪轨迹

常见的为 PID 控制  
再往后为：

```text
Pure Pursuit
Stanley
LQR
MPC
MPPI
```

### 点云生成

```python
sensor_lidar/src/scan_to_cloud_node.cpp
```

整体的逻辑为：

```text
订阅：

/scan_filtered
       ↓

laser_geometry::LaserProjection
       ↓

PointCloud2
       ↓

发布：

/cloud_filtered
```

就是将之前的二维极坐标转换为直角坐标系坐标：

$$
x=r\cos\theta\quad y=r\sin\theta
$$

代码部分为：

```c++
#include <ros/ros.h>
#include <sensor_msgs/LaserScan.h>
#include <sensor_msgs/PointCloud2.h>
#include <laser_geometry/laser_geometry.h>

#include <string>

class ScanToCloudNode {
public:
    ScanToCloudNode()
        : nh_(), pnh_("~") {
        pnh_.param<std::string>("input_topic", input_topic_, "/scan_filtered");
        pnh_.param<std::string>("output_topic", output_topic_, "/cloud_filtered");

        scan_sub_ = nh_.subscribe(input_topic_, 10, &ScanToCloudNode::scanCallback, this);
        cloud_pub_ = nh_.advertise<sensor_msgs::PointCloud2>(output_topic_, 10);

        ROS_INFO_STREAM("scan_to_cloud_node: " << input_topic_ << " -> " << output_topic_);
    }

private:
    void scanCallback(const sensor_msgs::LaserScan::ConstPtr& scan_msg) {
        if (scan_msg->ranges.empty()) {
            ROS_WARN_THROTTLE(2.0, "scan_to_cloud_node: received an empty LaserScan.");
            return;
        }

        sensor_msgs::PointCloud2 cloud_msg;
        projector_.projectLaser(*scan_msg, cloud_msg);
        cloud_pub_.publish(cloud_msg);
    }

    ros::NodeHandle nh_;
    ros::NodeHandle pnh_;
    ros::Subscriber scan_sub_;
    ros::Publisher cloud_pub_;
    laser_geometry::LaserProjection projector_;
    std::string input_topic_;
    std::string output_topic_;
};

int main(int argc, char** argv) {
    ros::init(argc, argv, "scan_to_cloud_node");
    ScanToCloudNode node;
    ros::spin();
    return 0;
}

```

**问题**：现在几个外参和一个内参还没有确定（用于雷达和相机之间的转换）

K,R（雷达和相机之间的真实旋转外参根本还没有填进去。）,T 都是占位符

```text
雷达点 P_lidar = [x, y, z]ᵀ   (雷达坐标系)

      │  R, T (外参: 雷达→相机)
      ▼
P_camera = R · P_lidar + T    (相机坐标系)

      │  K (内参: 相机→像素)
      ▼
[u, v] = K · P_camera / z     (像素坐标系)
```

#### K——相机内参矩阵
相机怎么把 3D 点投影到 2D 图像上：

$$
K=\begin{bmatrix}f_x&0&c_z\\0&f_y&c_y\\0&0&1\end{bmatrix}
$$

标定时就要标定 K（由焦距以及主点决定），还有就是相机的畸变系数  
标定的方法：（棋盘格标定法）

```text
步骤：
1. 打印黑白棋盘格，贴平板上
2. 从不同角度/距离拍 15~30 张图
3. 检测每张图的棋盘角点 (已知真实间距)
4. 求解 K 和畸变系数
```

使用的工具为：

```bash
# ROS 一键标定
rosrun camera_calibration cameracalibrator.py --size 8x6 --square 0.025
```

#### R — 旋转外参 (Rotation Extrinsic)
回答：" 雷达坐标系相对相机坐标系的朝向差多少 "，3×3 旋转矩阵。

$$
R=\begin{bmatrix}r_{11}&r_{12}&r_{13}\\r_{21}&r_{22}&r_{23}\\r_{31}&r_{32}&r_{33}\end{bmatrix}
$$

```text
典型安装（雷达在前，相机在后上方）：
相机坐标系:       雷达坐标系:
   z(前)            z(前)
   ↑                ↑
   |→ y(左)         |→ y(左)
  /                /
 x(下)            x(下)

两者通常只差一个固定角度（安装角），R 就是这个角度
```

#### T — 平移外参 (Translation Extrinsic)
回答：" 雷达相对相机偏移了多远 "，3×1 向量。

$$
T=\begin{bmatrix}t_x\\t_y\\t_z\end{bmatrix}
$$

```text
例：雷达装在相机正下方 0.1m、前方 0.05m
    → T ≈ [0, 0, 0.05] 或 [0, -0.1, 0.05]（取决于轴定义）
```

对上面的三个参数，可以使用联合标定的方法：

```text
原理：
  同一块棋盘格/标定板，同时被雷达和相机"看到"
      ↓
  相机：检测到棋盘角点的像素坐标 (u, v)
  雷达：检测到标定板平面的点云（得到平面方程）
      ↓
  建立 "3D雷达点 ↔ 2D像素点" 的对应关系
      ↓
  PnP 求解 → 得到 R, T
```

### link：
在 ROS 机器人模型里，一个 link 可以理解成：

> 机器人某个刚体部件所绑定的坐标系。

比如 `laser_link` 表示：

> 以激光雷达自身为原点建立的坐标系。

雷达测到一个点：

```text
x = 2 m
y = 0.5 m
```

实际上完整意思是：

> 这个障碍物在 laser_link 坐标系下，位于雷达前方 2 m、左侧 0.5 m。

而不是“整个地图中的位置”。

所以必须通过 TF：

```text
laser_link  
   ↓  
base_link  
   ↓  
odom  
   ↓  
map
```

把它转成其他坐标系下的位置。

### base_link：机器人的主体坐标系
我们小车的代码定义在后轴中心，轮轴高度处

而 `base_footprint`：机器人在地面上的投影中心：就是对 `base_link` 投影到地面平面上，用于 2D 

### odom
里程计坐标系

> 机器人从启动位置开始，靠轮编码器、IMU、视觉或者其他里程计累计计算出来的位置

机器人先向前走再转弯，相对于启动位置：

```text
x ≈ 2.5
y ≈ 0.8
yaw ≈ 45°
```

虽然优点是连续、平滑，但是缺点是长时间会漂

### map
整个实验室的固定世界坐标系（最全局的坐标）  
map 作为一个长期定位的需要

| 坐标系         | 谁产生         | 主要特点     | 作用         |
| ----------- | ----------- | -------- | ---------- |
| `map`       | SLAM / AMCL | 全局准确，可修正 | 地图、全局定位、规划 |
| `odom`      | 编码器/IMU/里程计 | 连续平滑，但会漂 | 短期定位、控制    |
| `base_link` | 机器人本体       | 跟着机器人移动  | 机器人自身坐标    |

### 整体：

```text
                 SLAM
                   │
                   ↓
map ──────→ odom
                   │
               Odometry
                   │
                   ↓
            base_footprint
                   │
                   ↓
              base_link
              /    |    \
             /     |     \
        Camera   IMU    LiDAR
```

### 关系

$$
\begin{equation}
    ^{map}T_{base}={}^{map}T_{odom}\cdot{}^{odom}T_{base}
\end{equation}
$$

> 机器人在 map 中的位置  
>         =  
> map → odom 的校正  
>         ×  
> odom → base_link 的连续里程计位置

> [!important]+ map 理解  
> map 是机器人的“全局位置估计参考系”，而**不是绝对真实位置**。（也就是 map 也是**预测出来的位置，只不过是修正过的**，稍微准确一点的参考）（而 odom 完全是为了控制连续产生的，误差会不断积累，但是又不能直接修改 odom 的值消除，所以需要 map 作为其消除误差后的真实位置预测值）

> [!tip]+ odom 的理解  
> 这个是完全正确的  
> 根据：
>
>> 轮编码器  
>> IMU  
>> 视觉里程计  
>> LiDAR odometry
>
> 不断在 odom 原点上进行积分：

$$
\begin{equation}
    \begin{gathered}x_{k+1}=x_{k}+\Delta x\\y_{k+1}=y_k+\Delta y\\\theta_{k+1}=\theta_k+\Delta\theta\end{gathered}
\end{equation}
$$

因为这样做是连续的，所以控制器要用 odom，而不是由传感器判断位置

但是：

> `map` 和 `odom ` 的原点没有要求必须相同。  
> 两者之间的修正不是修正 odom 坐标系下的机器人位置，而是坐标变换，使得这个位置为两个不同坐标系下的等价位置，从而达到不修改坐标值，但是不会发生偏移的问题（机器人坐标对齐）

#### 总的来说

> odom 坐标系由轮速计、IMU 或其他里程计连续积分得到，具有良好的局部连续性，但会随时间累积漂移。SLAM 或定位算法利用激光雷达、摄像头以及已有地图等环境观测，对机器人全局位姿进行修正，并通过调整 map→odom 变换补偿里程计漂移，而不会直接修改连续的 odom→base_link 变换。

然后：

> 全局规划通常在 map 坐标系下进行，而局部规划与控制通常更依赖连续的 odom/base_link 坐标。通过 TF 链

$$ map\rightarrow odom\rightarrow base\_link $$

可以在全局地图、里程计坐标系以及机器人自身坐标系之间进行位置转换。

最后：

> RViz 中显示的机器人位置同样是定位系统估计得到的 map→base_link 位姿，并非物理世界的绝对真值。若机器人自身定位存在误差，则地图中的目标点转换至机器人坐标系后也会产生相应误差，从而影响局部规划和控制。

> [!tip]+ 一句话：  
> map  
> = 我在整个世界中“估计”在哪里  
> odom  
> = 根据自身运动推算“我从启动以来走到了哪里“”  
> base_link  
> = 以我自己为原点，东西现在在我的前后左右哪里

```text
map → odom
```

> 就是：**全局定位系统对局部里程计累计误差的修正。**

### 建图和定位的关系

| 阶段      | 地图    | LiDAR | Odom | IMU    | 输出                  |
| ------- | ----- | ----- | ---- | ------ | ------------------- |
| SLAM 建图 | 一开始没有 | ✅核心   | 推荐   | 可选     | `/map` + `map→odom` |
| AMCL 定位  | 已有地图  | ✅核心   | ✅核心  | 通常不直接用 | `map→odom`          |

> LiDAR/Camera 负责“看环境，纠正我在哪里”；Odom/IMU 负责“根据自身运动预测我到了哪里”。

你现在通过激光雷达做 Scan Matching，直接得到的其实是：

> laser_link 坐标系在相邻两帧之间的运动

而导航、SLAM、控制真正希望得到的是：

> 机器人主体 base_link 在相邻两帧之间的运动

所以需要外参转换（在转弯时有明显的区别）

## 雷达里程计
- 初始操作：`source devel/setup.bash`
- `scan_matcher.cpp`：实现的是点 - 线 ICP（Point-to-Line Iterative Closest Point）。被 CMake 编译成静态库 `lidar_scan_matcher`：
- `lidar_odometry_node.cpp `：节点：

```text
/scan 回调
  ↓
1) preprocessScan: LaserScan → 二维点云
   - 距离过滤 (0.15 ~ 8.0 m)
   - 孤立点过滤 (与左右邻点距离 > 0.25 m 视为噪声)
   - 步长抽样 (point_stride=2)
   - 把点从 laser 坐标系 变换到 base_footprint
  ↓
2) publishDebugCloud: 发布预处理后的点云到 /lidar_odometry/preprocessed_cloud（RViz 可视化用）
  ↓
3) processScanMatching:
   - 第一次来：把当前帧存为 reference，发布零位姿 odom
   - 之后：用 ScanMatcher 求 current→reference 的 2D 刚体变换
   - isMatchAccepted 质量门禁 (correspondences / inlier / residual / 跳变 / 速度)
   - 通过：composePoses 累计到 odom_pose_，更新 reference
   - 不通过：丢弃该帧（不污染位姿）
  ↓
4) publishOdometry:
   - 发 /odom_lidar (nav_msgs/Odometry)
   - 发 /lidar_odometry/path (nav_msgs/Path)
   - 发 TF: odom → base_footprint
```

- `lidar_odometry.launch`：启动入口：

```xml
<node pkg="lidar_odometry"
      type="lidar_odometry_node"     ← 编译出来的可执行文件
      name="lidar_odometry_node">
  <rosparam command="load" file=".../lidar_odometry.yaml" />
  <param name="input_topic" value="$(arg input_topic)" />  ← 默认 /scan，可在 launch 时覆盖
</node>
```
